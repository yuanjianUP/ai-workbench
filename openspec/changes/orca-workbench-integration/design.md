## Context

现有插件原型使用私有存储，未在实际 Orca 中验证；本机 `orca-ide` 曾因 WSL socket 错误无法调用。Orca 插件面板不能直接联网，`taskSources` 扩展点仍为预留；实际可用接口以目标版本验证结果为准。

## Goals / Non-Goals

**Goals:** 保持 Orca 与新代码分离；先验证手动执行闭环，再接入外部来源；将不支持与未知状态明确展示。

**Non-Goals:** 修改或替换现有 Orca；首版实现多 Agent 编排；将 Git worktree 当作安全沙箱；默认自动执行外部任务或自动对外反馈。

## Decisions

1. 插件面板通过插件 worker 调用独立任务服务，服务以 TypeScript 编写，初期单机使用 SQLite。面板不能直接联网；相较于全部放进 Orca 插件，独立服务可以接收外部事件并保留任务状态。worker 与服务的通信方式、身份验证及部署边界须先验证，不能假定本机监听天然安全。
2. 任务服务保存任务和执行记录，Orca 负责工作区与 Agent 终端。记录 Orca 返回的标识、最近已知状态及时间；不能确认的结果显示未知，不能由启动成功推断任务成功。对比自行管理全部 Agent 进程，此方案优先复用 Orca，但不假设其提供停止、恢复或 worktree 创建 API。
3. 手动任务和外部事件共用任务模型，外部事件先校验来源、授权及去重，默认待用户处理。仅在明确配置授权规则后执行对外操作，避免事件重试造成重复副作用。GitHub 和飞书分别实现各自的验签、事件标识及重试语义。
4. 每个任务拟使用独立 worktree；在授予自动执行能力前，验证实际隔离机制、目录权限和凭据范围。若不能建立所需隔离，保持手动处理并明确标记能力不可用。
5. 原型私有存储与新服务数据不是自动共享的。初期保留原数据并提供明确的导入或导出路径，经用户确认后迁移；不覆盖或静默删除数据。

## Risks / Trade-offs

- [目标 Orca 版本或 WSL 环境不支持所需接口] → 先做版本匹配的能力验证，记录替代方案并阻止依赖功能上线。
- [启动结果或终端状态无法证明任务完成] → 使用未知状态，保留可审查的日志及人工确认入口。
- [服务与插件的通信被其他本机进程滥用] → 在实现前确定认证、监听范围、密钥存储和权限检查并测试拒绝访问。
- [重试或崩溃导致重复任务或对外操作] → 持久化来源事件标识和操作记录，处理不确定结果时先核对，避免盲目重试。
- [worktree 不提供进程和凭据隔离] → 验证容器或系统级控制；验证失败时不启用自动执行。

## Migration Plan

先独立运行服务并验证，再由用户审阅权限后加载插件；测试期间保留现有 Orca 和原型数据。上线时先启用手动任务，再逐一配置外部来源。回退时停用新插件和服务，保留数据库与原型数据以备恢复；外部连接分别停用。
